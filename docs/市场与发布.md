# 市场与发布

本仓库（**<https://github.com/yexi-fun/ZTools-Tauri-plugin>**）就是 ZTools-Tauri 的插件市场源。
仓库形态与参考项目 [ZToolsCenter/ZTools-plugins](https://github.com/ZToolsCenter/ZTools-plugins)
一致：**GitHub 公开仓库是插件与市场元数据的唯一来源，插件包与市场清单通过 GitHub Release 分发**。

本文说明仓库约定、Release 产物、CI 行为，以及 ZTools-Tauri 客户端是怎么把它们消费掉的。

> 想直接动手：看 [README](../README.md) 的「快速开始」与「发布流程」；
> 想从 ZTools 插件迁移：看 [与 ZTools 插件的差异](与ZTools插件的差异.md)。

---

## 1. 仓库即市场：四个约定

| 位置 | 作用 | 谁消费 |
| --- | --- | --- |
| `plugins/<目录>/` | 插件源码（清单 / 页面 / 图标 / README / CHANGELOG） | 构建脚本、市场详情页 |
| `categories-mapping.json` | 分类 → 插件**目录名**列表 + 分类图标 | 生成 `categories.json`、市场分类导航 |
| `layout.yaml` | 市场首页布局（banner / 最新发布 / 分类导航 / 随机推荐） | 市场前端 / 门户 |
| `icons/` | 分类图标与横幅 | 市场前端 / 门户 |

插件**自身**的市场信息（标题、描述、作者、图标、README、发布说明）都在插件目录里，
不需要额外维护一份"市场描述文件"：

| 市场字段 | 来源 |
| --- | --- |
| `name`（市场主键） | `plugin.json` 的 `id` |
| `title` / `description` / `author` / `version` | `plugin.json` |
| `logo` | 插件目录里的 `logo` 文件，构建时内嵌为 base64 |
| `readme` | 插件目录的 `README.md` |
| `releaseNotes` / `changelog` | 插件目录的 `CHANGELOG.md` |
| `size` / `sha256` | 打包产物 `.zpx` 实际计算 |
| `categories` | 由 `categories-mapping.json` 反查 |
| `downloadUrl` | 本次 Release 的资产地址 |

## 2. 本地跑通整条流水线

CI 跑的就是下面这几条命令，本地随时可以复现：

```bash
node scripts/sync-sdk.mjs                      # 刷新 vendor/ztools-sdk（可选）
node scripts/detect-changes.mjs --all          # 写 release/build-info.json（含发布版本号）
node scripts/build-plugins.mjs --all           # 打包 → release/<插件 id>-<版本>.zpx
ZTOOLS_PLUGINS_REPO=yexi-fun/ZTools-Tauri-plugin \
  node scripts/generate-plugins-json.mjs       # → release/plugins.json + release/categories.json
node scripts/verify.mjs                        # 自检（清单规则 / 页面元素 id / 包结构 / sha256）
```

`release/` 是纯产物目录（`.gitignore` 已忽略，只保留 `release/.gitkeep`），CI 会把它们上传到 Release。

| 参数 | 作用 |
| --- | --- |
| `--release-version <版本>` | 指定 Release 版本号（默认 `YYYY.MM.DD`，即 tag `v<版本>`） |
| `--plugin a,b` | 只构建指定插件目录（本地调试用） |
| `--all` | 忽略变更检测、全量构建 |
| `--download-base <前缀>` | 把清单里的下载地址改写成自己的镜像（本地联调用） |

### 2.1 只构建变动插件时会发生什么

CI 默认只构建"本次有改动的插件"（`detect-changes.mjs` 比较 `HEAD~1..HEAD` 的 `plugins/` 变更）。
`generate-plugins-json.mjs` 会把它与上一次发布合并：

1. 读取上一次发布的市场清单（CI 从最近一次 Release 下载成 `release/plugins.previous.json`）；
2. 本次构建的插件用**新条目**（旧版本压进 `versions` 历史）；
3. 其余插件沿用**旧条目**（保留旧 `downloadUrl`，指向历史 Release 资产）；
4. 被删除的插件目录从清单里剔除。

这也是"清单必须合并"的原因：不合并的话，只发一个插件会把其他插件从市场里挤掉。

### 2.2 CI 的三种情形（`.github/workflows/build-and-release.yml`）

| 情形 | 行为 |
| --- | --- |
| 普通推送（有插件改动） | 只构建变动插件 → 合并旧清单 → 创建/更新 Release |
| **首次发布**（仓库还没有任何 Release 且本次无插件改动） | 自动改为**全量构建**，保证仓库能产出第一个 Release |
| 纯文档 / 脚本改动（无插件改动，且已有历史 Release） | 只跑源码级自检，**跳过**构建与发布（不会失败） |

手动全量重发：Actions → **Build and Release Plugins** → Run workflow（勾选 `build_all`），
或在 `plugins` 输入框里填要单独构建的插件目录名。

## 3. Release 产物

当前最新 Release：**`v2026.10.09`**（<https://github.com/yexi-fun/ZTools-Tauri-plugin/releases/latest>），
含 5 个资产：

| 资产 | 说明 |
| --- | --- |
| `com.example.hello-ztools-1.0.0.zpx` | 示例插件（最小骨架） |
| `com.example.quick-note-1.0.0.zpx` | 示例插件（文件与授权） |
| `com.example.text-toolkit-1.0.0.zpx` | 示例插件（多指令） |
| `plugins.json` | 市场清单：插件数组（标题/版本/描述/logo base64/分类/大小/sha256/下载地址/README/CHANGELOG/版本历史） |
| `categories.json` | 分类数组：`{ key, title, description, icon, list[] }` |

Release tag 形如 `v2026.10.09`；包地址即
`https://github.com/yexi-fun/ZTools-Tauri-plugin/releases/download/v<版本>/<插件 id>-<版本>.zpx`。

**稳定清单地址**（客户端读的就是它，GitHub 会自动重定向到最新 Release 的同名资产）：

```text
https://github.com/yexi-fun/ZTools-Tauri-plugin/releases/latest/download/plugins.json
https://github.com/yexi-fun/ZTools-Tauri-plugin/releases/latest/download/categories.json
```

## 4. ZTools-Tauri 客户端怎么消费

### 4.1 默认数据源：GitHub 仓库（无需后端）

宿主（`ztools-net::market` 的 `MarketClient`）默认走 **GitHub 公开仓库**：

| 能力 | 实现 |
| --- | --- |
| 列表 / 搜索 | 拉 `releases/latest/download/plugins.json`，关键字**在客户端本地过滤** |
| 详情 + README | 清单条目的 `readme` 字段 |
| 版本历史 | 清单条目的 `versions` 字段（新→旧） |
| 分类标题 | 同目录 `categories.json`（拿不到就退化成分类 key，不影响列表与安装） |
| 下载 | 清单条目的 `downloadUrl`（Release 资产绝对地址），流式下载 + 进度事件 |

要点：

- **不需要 GitHub API、不需要 token**：用 `releases/latest/download/<文件>` 这个固定地址，
  不存在限流与鉴权问题，tag 变化也不用改代码；
- 清单在进程内缓存 **5 分钟**（设置页一次会连发列表/详情/版本三个请求，不该每次都拉一遍）；
- 下载地址支持三种写法：绝对地址原样使用、以 `/` 开头按**清单地址的 origin** 解析、
  其余相对地址拼在**清单地址所在目录**之后（因此本地镜像也能直接跑）；
- `MarketPlugin.name` **就是插件 id**，与本地注册表一致；
- `updatedAt` / `publishedAt` 必须是**整数毫秒**：宿主按 `u64` 反序列化，
  写成 `1791528700570.8271` 这种浮点会让整个响应被判为非法（本仓库踩过这个坑）；
- 清单里多给的字段会被忽略；`installed` / `installedVersion` / `updateAvailable` 由宿主自己补。

设置页会显示当前来源：设置 → **插件市场** 的副标题写着
「插件来自 GitHub 公开仓库 `yexi-fun/ZTools-Tauri-plugin`（读取最新 Release 的 plugins.json）」，
对应宿主命令 `market_source`（返回 `{kind,label,url}`）。

### 4.2 备选数据源：HTTP 接口（自建后端 / 验收 mock）

保留接口源是为了自建市场与自动化验收（`tools/t7-acceptance/market_acceptance.py` 就靠它起 mock）。
接口形状与只读参考实现一致，平台参数固定 `win32`：

| 用途 | 请求 | 响应 |
| --- | --- | --- |
| 列表 / 搜索 | `GET {base}/plugins?limit=&platform=&t=` | `{ "latest": [MarketPlugin] }`（关键字由客户端本地过滤） |
| 详情 | `GET {base}/plugins/latest?name=&platform=` | `{ "available": true, "plugin": … }` / `{ "available": false, "reason": "not_found" }` |
| README | `GET {base}/plugins/readme?name=` | `{ "content": "markdown" }` |
| 版本历史 | `GET {base}/plugins/releases?name=&limit=&offset=` | `{ "name", "currentVersion", "items": [{ version, releaseNotes, publishedAt, sourceType }] }` |
| 下载地址 | `GET {base}/plugins/download?name=` | `{ "zpxDownloadUrl": "…" }`（也接受 `downloadUrl`） |

本仓库的 `server/serve.mjs` 就是这 5 个路由的最小实现（数据源是 `release/plugins.json`
与 `release/categories.json`）：

```bash
node server/serve.mjs --port 8787                 # 只提供接口
node server/serve.mjs --download-base /packages    # 同时把包托管在本地（离线联调）
```

### 4.3 调试开关（仅 debug 构建生效）

| 环境变量 | 作用 |
| --- | --- |
| `ZTOOLS_MARKET_REPO` | 换成别的 `owner/repo`（例如 fork 或组织仓库） |
| `ZTOOLS_MARKET_MANIFEST_URL` | 直接指定清单地址（本地静态服务 / 内网镜像联调） |
| `ZTOOLS_MARKET_API_BASE` | 切到 HTTP 接口源（自建后端 / 验收 mock） |

优先级：`MANIFEST_URL` > `API_BASE` > `REPO` > 默认仓库。
⚠️ 这三个变量**只在 debug 构建生效**（`#[cfg(debug_assertions)]` 包住）；release 构建固定使用
默认 GitHub 仓库——这是宿主刻意的防劫持设计。要让发布版指向别的市场，需要改宿主的
`DEFAULT_MARKET_REPO`，或在其前面套一层自建服务。

### 4.4 自建 / 内网托管的三种做法

1. **本地服务**：直接用 `server/serve.mjs`，或按 4.2 的表格实现这 5 个路由；
   客户端用 `ZTOOLS_MARKET_API_BASE`（debug）指过去；
2. **镜像清单**：把 Release 资产同步到内网，用 `--download-base` 生成本地清单，
   再让客户端用 `ZTOOLS_MARKET_MANIFEST_URL` 指过去——客户端会按清单地址解析下载地址，
   照样能装；
3. **静态托管**：`.zpx` 放对象存储/CDN，清单按 4.1 的字段准备好即可。

局域网给别的机器用：`node server/serve.mjs --host 0.0.0.0 --port 9000`，对方指向你的 IP
（记得放行防火墙）。

## 5. 已知边界与注意事项

| 事项 | 说明 |
| --- | --- |
| `releases/latest/download` 的短暂 404 | 新 Release 刚创建时，这个别名可能几秒内还指向旧状态。客户端会给出「市场仓库还没有发布可用的清单（404）」的可操作提示，稍后刷新即可 |
| 首次发布需要一次 CI | 仓库没有任何 Release 时市场是空的；推送一次让 Actions 跑通即可（见 §2.2） |
| 清单体积 | 全部插件的元数据 + base64 图标都在 `plugins.json` 里，当前约 13 KB；插件数上千时需要考虑拆分（接口源模式天然支持分页） |
| 无签名校验 | 宿主当前不校验包签名；仓库侧提供 `sha256` 供 CI/分发链路自行比对（`verify.mjs` 会复核清单与磁盘包一致） |
| 不做账号体系 | 没有登录、评论、点赞、私有插件；这些属于后端能力，不在本仓库范围内 |

## 6. 与官方市场的关系

- 本仓库是**默认市场源**：ZTools-Tauri 的「插件市场」页面直接读它的 Release 资产；
- 官方后端（`z-tools.top/api/market`）与本仓库的 HTTP 接口源形状一致，
  将来要把这些插件搬到官方后端，`plugins.json` 的字段可以直接映射过去；
- 自建市场适合内网分发、团队私有插件、离线/半离线环境。
